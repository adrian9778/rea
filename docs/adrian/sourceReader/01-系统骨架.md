# 01 · 系统骨架

> REA 是一个**跑在你自己机器上的逆向工程后端**：它自己不猜答案，而是把「目标二进制/网页/固件」交给一批你自带的分析引擎（Hopper、Ghidra、IDA、objdump、radare2 系、浏览器、adb…），再把引擎的输出规整成带溯源的 **Evidence** 交回给调用方。调用方有两个：终端里的人（CLI）和 AI 代理（MCP）。
>
> 边界澄清：本篇只讲「系统由什么组成、请求怎么穿过它」。**不**讲具体 provider 协议（见 15~21）、**不**讲 Evidence 字段语义（见 06）。

## 0 速览

1. 用户执行的 `rea` 不是 Node 程序本体，而是一个 276 行的 **JS 分发器** [scripts/rea.mjs](file:///Users/vincent/workspace/16_AI/rea/scripts/rea.mjs)，它按 argv 决定四条路由中的哪一条，再去 `import` 对应的**已编译产物**。
2. 分发器先看产物在不在：`dist/` 缺失时不尝试任何自愈，直接打印「跑 `npm ci && npm run build:cached`」并 `exit 1`（`Const：runtimeFiles` 之后的首个分支）。
3. 只有两条**常驻**路径（`mcp` / `mcp --http`）会加载 MCP 运行时；其余全部是**一次性** CLI 路径，用完即退（`Const：isMcpMode`、`Const：isMcpHttpMode`）。
4. CLI 与 MCP 不是两套实现：两者都进 `src/application/` 的同一批工作流，差异只在适配器层（[src/cli.ts](file:///Users/vincent/workspace/16_AI/rea/src/cli.ts) 相对 [src/main.ts](file:///Users/vincent/workspace/16_AI/rea/src/main.ts) + [src/server/](file:///Users/vincent/workspace/16_AI/rea/src/server)）。
5. MCP 入口有一条**冷启动分流**：满足四个条件时走 `runDeferred`（用录制好的工具目录先应答，不构造分析校验器），否则走 `runEager`（`src/main.ts 函数：run +9~+22`）。
6. 依赖方向是单向向内的：`domain ← contracts ← provider ← application ← composition ← 适配器`；引擎协议与 provider 专有代码不得进入 domain/application（AGENTS.md「Architecture and Cleanup」）。

## 1 三种进程角色

```
你敲下的命令
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│ scripts/rea.mjs            一次性 Node 进程，纯路由，不分析   │
│  ├─ mcp            → dist/mcp/main.js        runEntrypoint   │
│  ├─ mcp --http     → dist/mcp/main.js        runMcpHttpEntrypoint
│  ├─ mcp doctor     → dist/cli-runtime/mcpDoctor.js
│  └─ 其它所有子命令 → dist/cli-runtime/cli.js  createCli().serve()
└─────────────────────────────────────────────────────────────┘
    │                                     │
    ▼ 常驻，stdio/HTTP 长连接              ▼ 一次性，跑完退出
┌────────────────────────┐      ┌────────────────────────┐
│ MCP 适配器              │      │ CLI 适配器              │
│ src/main.ts 生命周期    │      │ src/cli.ts 装配 Incur   │
│ src/server/ 工具注册    │      │ src/cli/*Commands.ts    │
└───────────┬────────────┘      └───────────┬────────────┘
            │        两者共用同一批工作流     │
            ▼                               ▼
      src/composition/  ← 生产装配根（工厂 / 可选 provider 独立加载）
      src/application/  ← 共享工作流（分析、会话、Doctor、Setup…）
      src/providers/    ← 引擎适配（hopper/ghidra/ida/native/browser/…）
      src/process/      ← 子进程监督与所有权
      src/contracts/    ← 调用方可见 schema
      src/domain/       ← 纯函数语义（Evidence / 错误代数 / 格式声明）
      src/config/       ← 环境变量校验
```

角色划分的**判据是进程寿命**，不是代码位置：CLI 每条命令一个进程，MCP 一个进程服务整个会话，因此只有 MCP 侧需要 owner/cleanup/shutdown 这一整套机制（详见 [13](13-Process层-子进程监督与所有权.md)、[09](09-Server层-MCP适配器.md)）。

## 2 分发器的四条路由

分发器在 `import` 任何重型模块之前完成判断，这一点是刻意的 —— 注释写明「Route production MCP before importing Incur」，而 Incur（CLI 框架）自带 `mcp add` 之类的注册子命令，必须先让 REA 自己的 MCP 运行时抢到 `mcp` 这个词。

| 路由 | 判据 | 加载的产物 | 寿命 |
|---|---|---|---|
| shell 补全 | `Const：isShellCompletion`（由 `cliBuiltinArguments.js` 的 `cliCompletionShell(env)` 判定） | `dist/cli-runtime/cliBuiltinArguments.js` | 一次性 |
| `mcp` | `args[0]` 是 `--mcp`/`mcp` 且 `args.length === 1` | `dist/mcp/main.js` | 常驻 |
| `mcp --http` | 是 `mcp` 入口 + `args[1]` 以 `-` 开头 + 后续含 `--http` | `dist/mcp/main.js` | 常驻 |
| `mcp doctor` | `productionMcpDoctorArguments(args)` 命中 | `dist/mcp/main.js` + `dist/cli-runtime/mcpDoctor.js` | 一次性 |
| 其余全部 | 默认分支 | `dist/cli-runtime/{cli,cliOutput,cliResultOutput}.js` | 一次性 |

两个值得注意的细节：

- **`mcp add --http` 不是 REA 的 HTTP 入口**。判据要求 `args[1]` 必须以 `-` 开头，因此 `mcp add --http` 仍归 Incur 的 `mcp add`；而 `mcp -h --http` 会抵达 HTTP 入口自己的 help（`Const：isMcpHttpMode` 上方的注释）。
- **`builtinArguments` 可能是 `undefined`**：`dist/cli-runtime/cliBuiltinArguments.js` 不存在时整个模块以 `undefined` 导入，后续全部用可选链调用。这意味着分发器在「源码态」（未构建）也能走完判断，最终由产物存在性检查给出唯一失败原因。

### 2.1 分发器还兼任「管道语义」的持有者

CLI 分支里有一整套围绕 `stdout` 的处理：读者提前关闭管道（`rea ... | head`）时，进程按 SIGPIPE 惯例退出码 **141** 结束而不报错（`Const：SIGPIPE_EXIT_STATUS`、`函数：guardClosedStdout +1~+9`）；JavaScript 分析 worker 的关闭被放在 `finally` 与 `exit` 回调两处，两处共享同一个 `closeCliJavaScriptResources`，且当「分发失败」与「关闭失败」同时发生时用 `AggregateError` 保住两个原因（顶层 `finally` 分支）。

这段代码没有任何分析语义，但它决定了「用户看到的退出码」和「worker 是否被留下无人认领」，属于骨架级事实。

## 3 MCP 入口：冷启动分流

`src/main.ts 函数：run +9~+22` 决定是否走轻量路径。四个条件全部成立才 `runDeferred`：

| 条件 | 锚点 | 含义 |
|---|---|---|
| 非 HTTP 传输 | `run+13`（`dependencies.transport !== "http"`） | 只有 stdio 默认入口享受优化 |
| 未配置 Hopper 目标 | `run+14`（`config.value.hopperTargetPath === undefined`） | [推导] 一旦要绑深度引擎，就必须真构造会话 |
| 输出 schema profile 为 full | `run+9~+11`（`REA_MCP_OUTPUT_SCHEMA_PROFILE` 未设或 `full`） | 精简 profile 需要真契约 |
| 未注入 createServer / loadOptionalProviders | `run+17~+18` | 测试替身会注入，注入即走完整路径 |

`runDeferred`（[src/main/deferredRuntime.ts](file:///Users/vincent/workspace/16_AI/rea/src/main/deferredRuntime.ts) `函数：runDeferred +6~+8`）的做法是读一份**录制的 MCP 工具目录**（`RecordedMcpCatalog`）先完成握手与 `tools/list`，把真实 server 延迟到第一次真正需要时 `materialize`；`OwnedMcpServers` 负责「包括被丢弃的发现实例在内，每个 SDK 创建的 server 都由我们拥有」。`run` 上方的文档注释交代了这条路径的意图：`Start discovery without constructing unused analysis validators.`

`runEager`（[src/main/eagerRuntime.ts](file:///Users/vincent/workspace/16_AI/rea/src/main/eagerRuntime.ts) `函数：runEager +12~+25`）则是完整装配：`parseConfig` → `createLogger("mcp")` → `new AnalysisSettings` → `createBinarySession(...)` → `AbortController` → `createShutdown(...)` → `startMcpTransport`。

## 4 CLI 入口：一次调用装配 50 组命令

`src/cli.ts 函数：createCli` 是纯装配，没有业务逻辑：

```
createCli+7   snapshotEnvironment(selectedEnvironment)   # 冻结一份环境快照，之后不再读活 process.env
createCli+8   createDirectAnalysis(environment)          # 从 composition 拿一次性分析能力
createCli+11  REA_LOG_LEVEL 解析；解析失败 → level 为 "silent"（doctor 例外，见分发器）
createCli+19  Cli.create(PRODUCT_IDENTITY.cliBinary, …)  # 依赖：incur
createCli+39  registerSetupCommands(cli, logger, environment)
createCli+39~+90  … 共 47 个 registerXxxCommands …
createCli+91  presentOmittableDefaults(cli)
createCli+93  rejectSurplusCliArguments(cli)   → serveStrict
createCli+95  excludeDeclaredSensitiveArguments(cli)
createCli+97  createCliCompletions(cli, environment)
createCli+98  重写 cli.serve = 补全 → strict 位置参数 → 敏感参数剔除 → 原 serve
```

三层包装的顺序是有意义的：**补全最先**（补全词是传输数据，允许出现半截的参数，不能走严格校验）→ **严格位置参数** → **敏感参数剔除** → 真正的命令处理。任何一层想改这条链，都要重新想清楚「代理传进来的 argv」在哪一步被规整。

`snapshotEnvironment` 值得单独记住：CLI 在入口就把环境复制成一份只读快照并向下传递，因此运行期修改 `process.env` 不会影响已装配的行为，测试也不必再伪造全局环境（同一函数被 MCP 入口 `run+3` 使用）。

## 5 源码 ↔ 构建产物映射

分发器只认 `dist/`，`src/` 从不被生产路径直接执行：

```
src/main.ts                → dist/mcp/main.js
src/cli.ts                 → dist/cli-runtime/cli.js
src/cliOutput.ts           → dist/cli-runtime/cliOutput.js
src/cli/cliResultOutput.ts → dist/cli-runtime/cliResultOutput.js
src/cliBuiltinArguments.ts → dist/cli-runtime/cliBuiltinArguments.js
src/mcpDoctor.ts           → dist/cli-runtime/mcpDoctor.js
src/**（其余）              → dist 下按 tsconfig/turbo 任务切分 [推导]
```

前六项来自 `Const：runtimeFiles` 的字面量，可直接证实；最后一行是推断，映射规则细节见 [25 构建与发布](25-构建与发布.md)。

`package.json` 的 `bin` 把 `rea` 与 `rea-agents` 两个命令名都指向 `scripts/rea.mjs`，所以「命令名」不影响路由。产品身份集中在 [src/identity.ts](file:///Users/vincent/workspace/16_AI/rea/src/identity.ts) `Const：PRODUCT_IDENTITY`（`cliBinary: "rea"`、`mcpServerKey: "rea"`、`configFileName: "rea.json"`、`skillName: "reverse-engineer-anything"`），注释明确说明集中化的目的是**防止长期存在的 client 注册项与 npm 包/可执行文件漂移**。

## 6 一次请求最短心智模型

后面三篇会把这条链拆开，这里只给骨架版：

```
调用方(MCP)                     适配器                工作流               引擎
tools/call ──▶ src/server/ ──▶ src/application/ ──▶ src/<provider>/ ──▶ 子进程 / bridge
   参数             schema 校验        会话与选取         协议帧         src/process/ 监督
                     ▲                  ▲                              │
                     │                  └──── src/composition/ 装配 ────┤
                     └──────── src/contracts/ 定义调用方可见形状          │
                                                                        ▼
                                              src/domain/ 规整为 Evidence（带溯源、带未知）
```

`src/domain/` 的纯度可以量化：159,019 行非测试代码里，**没有任何**非测试文件导入 `node:fs`/`node:child_process`/`node:vm`/`node:worker_threads`/`node:net`/`node:http`/`node:os`/`node:module`（对 `src/domain/**/*.ts` 排除 `*.test.ts` 与 `*.fixture.ts` 后逐个 grep，命中均为 0）。它导入的 Node 内建只有四类纯计算：`node:crypto`（21 个文件）、`node:path`（14）、`node:url`（2）、`node:zlib`（1）。所有对外部世界的触碰集中在 provider 与 `src/process/`。

> 反例值得注意：**测试**文件里确实有 12 个 `src/domain/**/*.test.ts` 导入 `node:fs` 等，用于制造真实输入，不代表域层有副作用。

## 7 边界与失败模式

| 现象 | 根因位置 | 说明 |
|---|---|---|
| `REA's compiled runtime is missing.` | `scripts/rea.mjs` 产物检查分支 | 未构建 / 构建被清理；REA 不会替你构建 |
| MCP 启动失败只打印固定句子 | `src/main.ts 函数：runEntrypoint +13` | 启动原因被**故意脱敏**（注释：unexpected failures must not leak internal details），细节只能从日志通道找 |
| `--update` 别名报错 | `src/cli.ts 函数：createCli +28~+32` | Incur 的 `update:false` 只压制通知、不压制安装器，REA 用抛错封掉歧义 flag，强制走 `rea update` |
| `rea ... \| head` 退出码 141 | `Const：SIGPIPE_EXIT_STATUS` | 视为「读者已拒收」，不报失败 |
| doctor 之外的命令因日志级别非法而停住 | `src/main.ts`/分发器的配置错误分支 | doctor 被特意放行，好让就绪报告能点名 `REA_LOG_LEVEL` |

## 8 问题清单

- **P2｜分流条件与「为什么」分散在两处**：`run+9~+16` 的四个条件是冷启动正确性的关键，但每个条件的原因没有逐条注释（仅 `run+88` 上方注释交代了「不构造未使用的分析校验器」这一层意图）。`hopperTargetPath === undefined` 这条尤其需要一次实验确认它是「必须真会话」还是「历史遗留」。→ 待拍板
