# 00 · 文档规范与定位约定

> 本篇是 `docs/adrian/sourceReader/` 全套文档的**唯一规范来源**。任何一篇的格式、锚点、事实口径与此冲突时，以此为准；发现此文档本身有漏洞，先补此文档再改其余篇。

## 1. 这套文档是什么

面向三类读者的源码走读库：

| 读者 | 诉求 | 对应层级 |
|---|---|---|
| 新手 | 不看源码也能明白系统由什么组成、一次请求怎么走 | 第一层（01/02）、第二层（03） |
| 熟手 | 改代码前定位到确切文件、函数、调用关系与约束 | 第三层（04/05）、第四层各模块篇 |
| 高手 | 边界条件、失败模式、设计权衡、未被源码回答的问题 | 每篇末的「问题清单」与「已知缺口」 |

产出目录：`docs/adrian/sourceReader/`（个人阅读库，不属于 VitePress 站点内容，不参与 `npm run docs:check`）。

## 2. 源码锚点：符号 + 偏移，禁止裸行号

行号随重构漂移，**正文一律不写裸行号**。锚点格式：

| 场景 | 写法 | 例 |
|---|---|---|
| 函数内某行 | `相对路径 函数：Foo 偏移：+N`（`+0` = 函数签名行，偏移 = 目标行 − 签名行） | `src/cli.ts 函数：createCli 偏移：+83` |
| 连续片段 | `Foo+0~+20` | `runEntrypoint+2~+13` |
| 非函数代码（类型/常量/顶层语句） | `Const：X` / `Type：X` / `Module：xxx` | `src/identity.ts Const：PRODUCT_IDENTITY` |
| 调用关系 | 标双方 | `调用方 run+96 ↓ 被调用方 parseConfig` |
| 第三方依赖 | 注明包名 | `依赖：incur`、`依赖：@modelcontextprotocol/server` |

**文末源码索引**是唯一的例外，允许 `文件:符号:绝对行号`，方便编辑器跳转复核；但该行的「符号」必须真实存在，绝对行号只作便利用途、不作论据。

校验方法（写完必跑）：正文里每个 `函数：Foo` 的 `Foo` 必须能在对应文件 grep 到；偏移必须落在该函数体内（`目标行 − 签名行`）。

## 3. 事实分级：四级标注

每条技术事实必须能归入一级，且**不可越级表述**：

| 级别 | 标记 | 判定标准 |
|---|---|---|
| 观察 | 无标记（默认） | 源码里直接读到的字面事实（函数名、字段、常量、分支、调用点） |
| 推导 | `[推导]` | 由多处源码组合推断，但没有单点源码直接写明 |
| 假设 | `[假设]` | 合理猜测，源码未证实，需实验或问作者 |
| 未知 | `[未知]` | 源码无法确定，写清「当前源码无法确定」与查证方向 |

红线：

1. **严禁编造**。字段有无、默认值、是否缓存、走哪条分支，必须 Grep/Read 查证后写。
2. **禁止「同上 / 略 / 以此类推」** 替代核心内容。
3. **未逐行读取的生成代码、第三方依赖内部实现、Python/Java bridge 未读部分**，显式标注「未读取，不臆测」。
4. **实测数据**（跑命令得到的输出、性能数字）必须标注环境：提交号、Node 版本、平台、日期；无则写「未实测，待补」。

## 4. 图不能少

- 每篇 ≥1 张图。
- 数据流 / 报文 / 内存布局 → **ASCII 字符图**（可对齐、可复制进终端）。
- 架构 → Mermaid `flowchart`；调用链 → `sequenceDiagram`；会话与生命周期 → `stateDiagram-v2`；多实体关系 → `erDiagram`（有表/多结构关系时必须用）。
- 图里的每个节点名必须能在正文或源码索引中找到对应锚点。

## 5. 单篇文档骨架（统一段落顺序）

```
# NN · 标题
> 一句话定位（是什么、属于哪一层/哪个进程、边界澄清：不要与相邻概念混淆）
## 0 速览            —— 3~6 条硬结论，每条带锚点
## 1..N 正文         —— 按主题顺序展开，代码贴精简片段并标 Foo+偏移
## 边界与失败模式     —— 该模块「什么时候会静默出错」
## 问题清单           —— 按 P1/P2/P3 分级；未决策项单列「待拍板」，每条给锚点
## 已知缺口            —— 区分「风险」与「设计特性」
## 源码索引           —— 文件:符号:绝对行号（跳转便利）
## 相关篇             —— 上下游导航
```

Provider 族文档（15~21）额外要求：**能力表作为唯一路由真相源**（该 provider 暴露哪些工具/命令、由哪个 register 文件挂载、契约定义在哪），以及 **bridge 协议帧的字节级布局**（有 ASCII 图）。

## 6. 语言与术语

- 正文中文，短句优先，少用术语；必须用的术语保留英文原词并在首次出现时一句话解释。
- 函数名、类型名、字段名、错误码、文件路径、命令一律英文原文 + `code` 标记。
- 不翻译代码里的错误消息原文。

## 7. 写作流程（每篇必做）

1. 读 [README.md](README.md) 确认本篇边界与相邻篇分工，避免重复。
2. 读 `docs/architecture.mermaid` 与 `AGENTS.md`，确认本篇涉及的层归属。
3. 读源码本体（不读 `docs/` 既有文档作为事实来源——它们可能漂移，仅作交叉印证；若引用必须标 `[推导]` 并回源码验证）。
4. 写正文 → 自查锚点可解析 → 自查事实分级 → 补图 → 补问题清单。
5. 回填 README 导航表的状态列与「最近更新」。

### 7.1 机械校验（每篇写完必跑）

```bash
node docs/adrian/sourceReader/tools/anchor-check.mjs docs/adrian/sourceReader
```

它检查三类锚点：`路径 函数：X 偏移：+N`（文件存在 + 符号存在 + 偏移落在函数体内）、`路径:X:N` 形式的文末索引（该行确实含 X）、以及 `Const：X`/`Type：X` 与 `X+N` 短锚点（在同行提到的文件里存在；同行没写文件时退化为「在 `src/` 下任意处有定义」）。

已知局限，读数时记住：

- **不检查 `00-` 自身**（本篇里的 `Const：X` 是模板占位符，不是锚点）。
- 函数体范围靠**括号/缩进启发式**估算，遇到跨行参数列表里的对象字面量可能估错，报 `offset-out-of-body` 时要人工确认再改文档。
- 短锚点的退化判据只保证「这个名字存在」，不保证「在这段代码里」—— 报告里出现 `short-anchor-unknown-symbol` 一定是编造，出现其它类别时仍需人工回读。

## 8. 仓库特有的口径约定

- **分层依赖方向**：`domain ← contracts ← provider ← application ← composition ← CLI/MCP`。写作时先判定被讨论代码属于哪层，跨层调用要指出是否属于 AGENTS.md 说的「引擎协议与 provider 专有代码不得进 domain/application」。
- **证据（Evidence）语义**：REA 的核心产出是带溯源的 Evidence，不是自由文本结论。描述任何返回值时，说清它是观察、推导还是未知。
- **所有权（ownership）**：子进程、私有目录、lease 的「谁拥有、谁负责清理」是本仓库的一等概念。凡涉及生命周期，必须写明 owner 与 cleanup 失败后的保留行为。
- **只读边界**：Ghidra 用临时库不改目标字节；IDA 分析只读、绝不保存或关闭 GUI 数据库。描述 provider 时明确其副作用面。
- **不写**：安装步骤、用户手册、provider 购买建议——那些属于 `docs/` 既有文档，本库只讲源码机制。
