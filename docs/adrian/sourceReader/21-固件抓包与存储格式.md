# 21 · 固件、抓包、信号、SQLite 与参考源：六个「读制品/驱工具」provider 的实现层

> 定位：`src/firmware/`、`src/pcap/`、`src/captures/`、`src/signals/`、`src/sqlite/`、`src/reference/` 六个 provider 实现目录（provider 层，CLI/MCP 之下的适配层）。本篇讲**实现**：认什么格式、把什么交给外部工具、失败返回什么 tag、上限在哪一层。装配点（谁 `new` 了谁、`xxxHostSupported` 从哪儿 re-export）在 `11-Composition层-生产装配根.md` §2.4 已列表化，本篇只回链不重复。
>
> 边界澄清：`src/reference/` **不是**签名库、**不是**官方文档快照，它读的是「参考源码树」（历史版本的目标代码），产物归属 19 篇的 AgentEnv/参考导入流程；本族里唯一把 `authority` 判成 `historical-reference` 的两个模块是 `reference` 与 `pcap`（§5、§3）。HAR/SAZ/QLOG 那些 Web 采集制品不在本篇，见 19 篇。

## 0 速览

1. **这六个目录不是「三个解析离线格式 + 三个驱动外部工具」的整齐对分**。按源码事实分：真正**在 REA 进程内自己解析二进制格式**的只有固件族里的 devicetree（`src/firmware/devicetree/DevicetreeParser.ts 函数：parseDevicetree 偏移：+0`）；固件的容器/压缩/文件系统识别、pcap 的报头与报文解析、信号录波的解码，全部**外包给调用者自带的工具**（Binwalk / Unblob / tshark / capinfos / sigrok-cli）；`sqlite` 用 Node 自带的 `node:sqlite` 原生引擎；`reference` 是纯 REA 内的目录树遍历器。证据见 §1 表格。
2. **本篇六个目录里的四个 `xxxHostSupported` 全部只看 `platform`，不看 PATH**：`src/firmware/FirmwareCommand.ts 函数：firmwareHostSupported 偏移：+0` 判 `=== "linux"`；`src/captures/TsharkCaptureProvider.ts 函数：tsharkHostSupported 偏移：+0` 判 `=== "linux"`；`src/signals/SigrokRecordingProvider.ts 函数：sigrokHostSupported 偏移：+0` 判 `=== "linux"`；`src/domain/pcap/pcapAnalysis.ts 函数：pcapCaptureHostSupported 偏移：+0` 判 `linux || win32`。`sqlite` 与 `reference` **没有** `xxxHostSupported` 符号（grep 范围见 §1.3）。工具是否存在于 PATH 走的是另一条链路（可用性探测，§6）。
3. **`captures` 与 `signals` 都不做硬件采集**：两者的结果 schema 把 `hardware_acquisition` 钉成字面量 `"not-performed"`（`src/domain/captures/packetCapture.ts Const：packetCaptureSchema`、`src/domain/signals/signalRecording.ts Const：signalRecordingSchema`），即 tshark 只 `-r` 读录制文件、sigrok-cli 只 `--input-file=` 读录制文件。
4. **`pcap` 与 `captures` 的分工不是「离线 vs 实时」，而是「摘要 vs 字段」**：`src/pcap/` 跑 `inspect_pcap_client` / `inspect_pcap_capture`（capinfos 摘要 + tshark JSON 聚合，带**可强制执行的原生内存边界**，Linux/Windows），`src/captures/` 跑 `inspect_packet_capture` / `inspect_packet_fields`（逐包字段抽取与字段词典发现，仅 Linux，靠 `prlimit`）。见 §3。
5. **`sqlite` 从不打开调用者的原库**：先把「库 + `-wal` + `-journal`」冻结成私有快照，再以 `readOnly: true` 打开**快照副本**（`src/sqlite/SqliteDatabaseInspection.ts 函数：inspectSqliteDatabaseSnapshot 偏移：+4`）。
6. **`FirmwarePartialObservation` 是 06 篇 `AnalysisPartialObservation` 联合的成员之一**，它只在「分析已完成但私有运行时清理未确认」时产生（`src/firmware/FirmwareProvider.ts 函数：completedFirmwareObservation 偏移：+2`，`kind: "firmware"`）。

### 1.2 命令行的选择：绝不安装、绝不搜索 PATH 的两种写法

固件族要求**绝对路径 + 环境变量**，不接受 PATH 搜索：`src/firmware/FirmwareCommand.ts 函数：resolveFirmwareCommand 偏移：+10` 处，只要 `!firmwareHostSupported(process.platform)`、或变量未设、或值不是绝对路径，立刻抛 `AnalysisCapabilityUnavailableError`；签名上方的注释写明「never install or search for engines」。变量名来自单一真相源 `src/contracts/firmware/firmwareToolRequirements.ts Const：FIRMWARE_TOOL_REQUIREMENTS`：`REA_BINWALK_COMMAND`（Binwalk 3.1.x，锚定 revision `4fdab3d4…`）与 `REA_UNBLOB_COMMAND`（Unblob 26.6.x，锚定 revision `1fcc7a0a…`）。

pcap 族允许 PATH 或环境变量两条路：`src/pcap/PcapConfiguration.ts Const：TSHARK_COMMAND_ENV`（`REA_TSHARK_COMMAND`）、`Const：CAPINFOS_COMMAND_ENV`（`REA_CAPINFOS_COMMAND`），其 `Const：TOOL_REMEDIATION` 原文要求「Supply Wireshark 4.x tshark and capinfos on PATH or through absolute … ; REA does not install them」。`[观察]` 这是本族里唯一「可以让工具躺在 PATH 上」的地方。

### 1.3 `xxxHostSupported` 由什么决定：只有平台，没有 PATH

四个已存在的 `HostSupported` 谓词都是**纯平台函数**，参数即 `NodeJS.Platform`，不触碰文件系统：

```
src/firmware/FirmwareCommand.ts 函数：firmwareHostSupported 偏移：+0
  platform === "linux"
src/captures/TsharkCaptureProvider.ts 函数：tsharkHostSupported 偏移：+0
  platform === "linux"
src/signals/SigrokRecordingProvider.ts 函数：sigrokHostSupported 偏移：+0
  platform === "linux"
src/domain/pcap/pcapAnalysis.ts 函数：pcapCaptureHostSupported 偏移：+0
  platform === "linux" || platform === "win32"
```

`[观察]` `pcap` 多一个 `win32`，原因写在紧邻的 `src/domain/pcap/pcapAnalysis.ts Const：PCAP_CAPTURE_UNSUPPORTED_HOST_REASON`：摘要类操作需要「可强制执行的原生内存边界」——Linux 靠 util-linux `prlimit`，Windows 靠 Job Object；其它平台没有可强制边界，所以判不支持。也就是说：`HostSupported` 编码的是**边界能力**，不是「工具装没装」。

工具装没装是第二道门，走可用性探测：`src/pcap/PcapProvider.ts 函数：inspectAvailabilityAdmitted 偏移：+5` 先查 `pcapCaptureHostSupported(process.platform)`（返回 `code: "unsupported_host"`），再 `await this.prepareCaptureBound()`，失败时把 `PcapConfigurationFailure` 映射成配置类 code、其余映射成 `"executable_missing"` / `"version_unresolved"`。

**证伪**：`src/sqlite/`、`src/reference/` 中不存在 `sqliteHostSupported` / `referenceHostSupported` 之类的符号。grep 范围与结论：`grep -rn "HostSupported" src --include="*.ts"`（排除 `*.test.ts`）的全部命中文件是 `src/pcap/PcapNativeBound.ts`、`src/pcap/PcapProvider.ts`、`src/captures/TsharkCaptureProvider.ts`、`src/firmware/FirmwareCommand.ts`、`src/native/pwntools/PwntoolsDecoder.ts`、`src/signals/SigrokRecordingProvider.ts`、`src/server/createServer.ts`、`src/composition/*.ts`、`src/evm/EvmoleInterfaceProvider.ts`、`src/javascript/recovery/WakaruCommand.ts`、`src/domain/pcap/pcapAnalysis.ts` —— 其中**没有** sqlite/reference 条目，即 `src/sqlite/`、`src/reference/` 未导出该形状符号。`[推导]` 它们的宿主限制改由别处表达：sqlite 用原生 API 能力判据（§4.3），reference 用 `noFollowOpenSupported()`（`src/reference/ReferenceSourceReaderValidate.ts 函数：noFollowOpenSupported 偏移：+0`）。

## 2 固件族：认什么、partial 是什么、截断怎么处理

### 2.1 识别的层次：REA 不自己认容器，只归一化工具的报告

`inspect_firmware_regions` 的输出形状（`src/domain/firmware/firmwareAnalysis.ts Const：firmwareResultSchemas`）里，`regions[]` 每项带 `provider_id / offset / reported_size / signature / description / reported_confidence`，并且 `size_basis` 被钉成唯一字面量 `"provider_reported_validation_unknown"`、`coverage` 钉成 `"signature_scan"`。`[观察]` 这两条字面量就是「REA 不背书工具识别结果」的代码化表达：签名命中和上报长度不代表分区有效、不代表未加密、不代表运行时映射成立——`src/firmware/FirmwareProvider.ts Const：limitations` 的第一条正是这句话。

`extract_firmware` 一侧保留 `files[]`（含 `sha256`、`reported_sha256`、`mime_type`、`analysis_depth`、`runtime_address: null`、`original_file_range: null`）、`chunks[]`、`derivations[]`、`extraction_gaps[]`、`unpublished_entries[]`，以及 `coverage: "complete" | "partial"`。容器/压缩/文件系统的**识别者是 Unblob**，REA 只做形状归一化：`src/firmware/FirmwareReports.ts 函数：normalizeBinwalkReport 偏移：+0` 与 `函数：normalizeUnblobReport 偏移：+0`。`[观察]` `FirmwareReports.ts` 自己定义 `signature`（`id/offset/size/name/description`）与 `integer` 校验器，把工具 JSON 先解成受约束形状再进 domain。

架构（CPU 架构、运行时地址）在本族里**没有**被识别：`runtime_address` 恒为 `z.null()`。`[假设]` 这属于刻意留白，因为架构判定归 Ghidra/IDA 族（未在本族源码中找到反证，也未逐文件确认其它 provider）。

### 2.2 唯一自研的二进制解析：扁平化设备树（FDT/DTB）

`src/firmware/devicetree/DevicetreeParser.ts 函数：parseDevicetree 偏移：+9` 处校验前 4 字节魔数 `0xd00dfeed`，不符抛 `BinaryFormatFailure("unsupported", "Not a flattened devicetree blob")`；`+14` 处校验 `version` 只接受 16/17（v17 头 40 字节、v16 头 36 字节）；`bytes.length < 28` 或 `< headerBytes` 走 `malformed("Truncated FDT header")`；`totalsize > bytes.length`、`totalsize < headerBytes`、`last_comp_version > version` 一律 `malformed("Invalid FDT header size or compatibility version")`。长度 256 之外的字符串值在 `+233` 处（`truncated: length > 256`）显式标记为截断，而不是悄悄截。

`src/firmware/devicetree/DevicetreeProvider.ts` 把它接进 `DevicetreePort`（application 层端口在 `src/application/binaryDiagnostics/DevicetreePort.ts`），说明 devicetree 走的是 **binaryDiagnostics** 装配线而不是 `composition/firmware.ts`（`[推导]`：该文件 import `application/binaryDiagnostics/DevicetreePort`，回链 11 篇 §2.4 的 `binaryDiagnostics.ts` 工厂行）。

### 2.3 「partial observation」在固件里指什么

`FirmwarePartialObservation` 定义在 `src/domain/firmware/firmwareAnalysis.ts Type：FirmwarePartialObservation`：`{ kind: "firmware"; result; provenance? }`，docstring 是「Completed firmware result retained when private-runtime cleanup cannot be confirmed」。它作为成员进入 06 篇的联合类型：`src/domain/analysisErrorBase.ts Type：AnalysisPartialObservation 偏移：+30` 处列出 `| FirmwarePartialObservation`（该联合起始于 `+0` 的 `export type AnalysisPartialObservation =`）。

生产点只有一个：`src/firmware/FirmwareProvider.ts 函数：completedFirmwareObservation 偏移：+2`（`kind: "firmware"`），`provenance` 里装 `raw_result / provider / subject / locations / limitations / analysis_profile`。它在同文件三处被塞进 `Result` 的 `partialObservation`（调用点在 622、663、676 附近，见源码索引），语义都是「分析产物已到手，但运行时目录清理没确认」→ 返回 `err(...)` 且带 `partialObservation`，绝不因为清理失败而丢掉已完成的结果。这与 `AGENTS.md`「Retain ownership of resources whose cleanup failed」「Preserve partial facts」直接对应。

### 2.4 缺口与未知偏移：`extraction_gaps`

`src/domain/firmware/firmwareAnalysis.ts Const：extractionGap` 是本族处理「被截断/未能处理」的中心装置。`kind` 枚举七个值：`missing-extractor-dependency`、`unknown-chunk-handler`、`unclassified-range`、`encrypted-chunk`、`depth-limited`、`extractor-failure`、`unpublished-entry`。字段设计上刻意区分「有偏移」与「只有身份」：`range` 与 `root_file_range` 都 `.nullable()`，注释写明 `provider_id`「does not imply a byte range」；`relative_path`、`handler` 同样 nullable；`continuation_id` 是查询 `extraction_continuations` 表的键。`[观察]` 也就是说：**未知偏移就写 null，不用 0 或猜测值占位**，并且缺口不推断成镜像损坏（`src/firmware/FirmwareProvider.ts Const：limitations` 第四条：「A listed gap does not mean the target is corrupt」，原文为英文，此处节引）。

另一处「跨源事实会漂移」的诚实记录：`src/firmware/FirmwareProvider.ts Const：UNBLOB_LINK_TARGET_LIMITATION`——软链 `link_target` 取自 Unblob 抽出的树而不是镜像文件系统元数据，绝对目标被 Unblob 改写成相对形式，因此相对路径可能在镜像里本是绝对路径。

## 3 pcap / captures / signals：谁解析格式，谁串起来

**三个都不是「实时采集」。** `signals` 与 `captures` 的结果 schema 都把 `hardware_acquisition` 钉成 `z.literal("not-performed")`（`src/domain/captures/packetCapture.ts Const：packetCaptureSchema`、`src/domain/signals/signalRecording.ts Const：signalRecordingSchema`），实参里 tshark 用 `-r`（`src/captures/TsharkCaptureProvider.ts Class：TsharkCaptureProvider`，参数构造在同文件 305-325 行区），sigrok-cli 用 `--input-file=./<snapshotName>`（`src/signals/SigrokRecordingProvider.ts Class：SigrokRecordingProvider`，同文件 329-343 行区）。`[观察]` 后者的路径写法带注释解释「用 `./` 前缀把快照文件名和 sigrok 的 stdin 操作数 `-` 区分开」。

分工因此是按**输出粒度 + 边界强度**划的：

- `src/pcap/`：文件级摘要与聚合。输入契约 `src/domain/pcap/pcapAnalysis.ts Const：pcapInputSchemas` 只有两个操作 `inspect_pcap_client`（自检 tshark/capinfos 安装与注册）与 `inspect_pcap_capture`（对一个本地 pcap/pcapng 文件出摘要）。它的独占特征是**可强制执行的原生内存边界**：`src/pcap/PcapNativeBound.ts 函数：preparePcapNativeBound 偏移：+8` 给 Windows 装 1 GiB Job Object committed-memory 上限；`偏移：+17` 处对不受支持平台先抛 `AnalysisCapabilityUnavailableError`；Linux 分支（同函数后半段）用 `prlimitCeilingArguments` + `BOUNDED_PRODUCER_LIMITS`（`address_space_bytes`、`file_bytes`）和 `Const：PCAP_CPU_SECONDS` 组出 `prlimit` 参数。
- `src/captures/`：逐包字段与字段词典。操作 `inspect_packet_capture` / `inspect_packet_fields`，在 `src/captures/TsharkCaptureProvider.ts 函数：#executeRequest 偏移：+4` 处按 `"path" in input` 分流；边界靠 `REA_TSHARK_PRLIMIT_COMMAND` 指定 `prlimit` 路径、默认 `/usr/bin/prlimit`；同一个变量名有**两种读取写法**：`src/captures/TsharkCaptureProvider.ts 函数：#executeRequest 偏移：+39` 直接以字面量键读 `this.environment`，`src/pcap/PcapNativeBound.ts Const：PRLIMIT_COMMAND_ENV` 则先定义常量、再由 `函数：preparePcapNativeBound 偏移：+26` 读取。参数向量由 `src/process/LinuxResourceLimits.ts 函数：prlimitArgumentVector` 生成；tshark 侧在 `函数：#executeRequest 偏移：+51` 拿到 `limitArguments`，`偏移：+58` 的 `execute` 闭包把它前置到工具参数之前（`偏移：+63`）。
- `src/signals/`：录波解码。操作 `decode_signal_recording` / `inspect_signal_decoders`（`src/signals/SigrokRecordingProvider.ts 函数：#executeRequest 偏移：+4` 同样按 `"path" in input` 分流），并发上限在 `Class：SigrokRecordingProvider` 的构造里钉成 `details: { max_concurrent_decodes: 1 }`。

`[观察]` tshark 的 `-r <快照文件>` 与 sigrok-cli 的 `--input-file=./<快照文件>` 都出现在各自 `函数：#executeRequest` 的参数组装段；后者的 `./` 前缀带注释解释「把快照文件名和 sigrok 的 stdin 操作数 `-` 区分开」。

**把两者串起来的是 Evidence 而不是代码复用**：`src/domain/pcap/pcapEvidence.ts 函数：createPcapEvidence 偏移：+14` 处，`inspect_pcap_capture` 的 `confidence` 判为 `"derived"` 且 `authority: "historical-reference"`，其它操作保持默认（不写 `authority`、confidence 为 `"observed"`）。`[推导]` 理由是聚合/摘要值由 capinfos 推断（例如截断帧的推断长度，见 `src/pcap/PcapOutput.ts 函数：parseCapinfosOutput` 对重复标签的注释），属于「派生的历史参考」而非直接字节观察。

**位置信息**：pcap 侧 locations 只有 `[{ kind: "artifact-path", path }]`（`src/pcap/PcapProvider.ts` 102 行），**没有**报文级偏移。`[观察]` 因此 pcap 族的位置粒度是「整文件」。

**边界一句话指向**：HAR / SAZ / QLOG 这类 Web 采集制品（`src/domain/qlogCapture.ts`、`src/domain/webNetworkCapture.ts` 等）不属于本篇的六个模块，归属 19 篇。

## 4 sqlite：只读、WAL、位置粒度

### 4.1 只读是怎么保证的：快照 + 五重连接参数

`src/sqlite/SqliteDatabaseSnapshot.ts 函数：captureSqliteDatabaseSnapshot 偏移：+8` 起，把 `[path, path+"-wal", path+"-journal"]` 三个成员当**一个文件集**统计、复制进私有目录（`Const：member` 类型的 `"WAL" | "rollback journal"` 用于命名出错的成员；`函数：verifyInactiveJournal 偏移：+0` 校验 journal 处于非活跃状态）。原库从未被 SQLite 打开——这是 `src/sqlite/SqliteDatabaseInspection.ts 函数：inspectSqliteDatabaseSnapshot 偏移：+37` 处 `limitations` 第二、三条的字面承诺：「The source database and WAL are never opened by SQLite or modified. A private copy may acquire its own WAL-index sidecar and is removed after inspection.」

连接本身是 Node 原生 `DatabaseSync`（`grep` 范围内 `src/sqlite/` 无 `sqlite3`/`better-sqlite3` 依赖；`src/kuna/` 里的 `sqlite3` 字样是反编译目标符号，与本族无关）：

```
src/sqlite/SqliteDatabaseInspection.ts 函数：inspectSqliteDatabaseSnapshot 偏移：+4
  new DatabaseSync(snapshotPath, {
    readOnly: true, allowExtension: false, readBigInts: true,
    enableDoubleQuotedStringLiterals: false, timeout: 0,
    limits: { length: …outputBytes, sqlLength: …outputBytes },
  })
```

随后 `偏移：+28` 处一次性执行 `PRAGMA trusted_schema=OFF; PRAGMA query_only=ON; PRAGMA mmap_size=0; PRAGMA cell_size_check=ON; BEGIN;`。`[观察]` `readOnly` 与 `query_only` 双保险，`mmap_size=0` 关掉内存映射以让内存边界可预测，`cell_size_check` 用来在损坏页上尽早失败。没有 `OPEN_READONLY` 常量——`grep -rn "OPEN_READONLY" src/sqlite` 无命中，本族用的是 `node:sqlite` 的选项对象而非 C 标志位。

执行隔离在 worker 子进程里：`src/sqlite/SqliteDatabaseWorkerExecution.ts 函数：executeSqliteDatabaseWorker 偏移：+0`，请求/回应用文件路径传递（`src/sqlite/SqliteDatabaseWorker.ts 函数：requestSchema` 附近要求 `snapshot_path` / `reply_path`）。

### 4.2 损坏库与「不能证明损坏」

本族刻意不做损坏断言。`src/sqlite/SqliteDatabaseInspection.ts 函数：rowEvaluationFailure` 一带的消息原文：「SQLite cannot prepare or evaluate rows of table … on REA's read-only connection」；`src/sqlite/SqliteDatabaseWorkerExecution.ts` 的 123 行原文强调「an unidentified query failure does not establish database corruption」，并建议改用 `schema_scope: database` 只取声明。`[观察]` 拒绝原因是枚举化的 `SqliteInspectionFailure` reason：`format | selection | column-selection | column-evaluation | row-evaluation | column-limit | unsupported | unavailable | output-limit | memory`（`src/sqlite/SqliteDatabaseLimits.ts Class：SqliteInspectionFailure`）。

### 4.3 「只读」的第二道门：原生 API 能力判据

`inspectSqliteDatabaseSnapshot` 用 zod 校验 `db.limits` 是否真的可读写回上限，不满足就抛 `SqliteInspectionFailure("unavailable", …)` 并指名要求「Node.js 24.15 or newer in the supported 24.x line, or a compatible Node.js 26+ runtime」。`[观察]` 也就是说 sqlite 的宿主准入是**API 能力检测**，而不是平台检测——这解释了 §1.3 里它没有 `sqliteHostSupported`。

### 4.4 位置粒度：到文件，不到页

`src/sqlite/SqliteDatabaseProvider.ts 函数：createSqliteObservation 偏移：+4` 构造 locations：先是 `{ kind: "artifact-path", path }`，`偏移：+8` 处若 `report.wal !== null` 追加 `-wal` 的 `artifact-path`。`[观察]` 没有行号/页偏移类 location kind；`limitations` 第五条明说「bytes_hex and encoding preserve SQLite's text byte representation, not original on-disk page offsets」。表名/列名在 result 里，不在 locations 里。Evidence 通过 `createEvidence(...)`（同文件 525 行附近）与 `partialObservation`（443、503、516 行附近）两条路落地，清理失败时同样保留已完成事实。

## 7 预算与上限：哪一层给的

06 篇 §6 的不变量「工作流集合无人为上限」在本族**没有被违反**：六个模块都没有「最多 N 个模块/N 个缺口/N 个表」这类**枚举封顶**，`chunks`、`derivations`、`extraction_gaps`、`unpublished_entries`、`entries`、`tables` 全是无界 `z.array(...)`。存在的上限都能归到三类真实约束：

| 上限 | 层 | 是否可调用者调 | 锚点 |
|---|---|---|---|
| 固件 staging 条目/字节预算 `max_output_files` / `max_output_bytes` | 资源约束（私有暂存区） | 可，到 schema 最大值；到顶后 remediation 明说「Raising … further is not supported」 | `src/firmware/FirmwareFiles.ts 函数：firmwareStagingBudgetRemediation 偏移：+0`、`函数：firmwareStagingLimit 偏移：+0` |

| 固件阶段预算 `analysis_timeout_ms` / `publication_timeout_ms` | 协议/调用者选择（上限 `MAX_FIRMWARE_TIMEOUT_MS`，默认 120000） | 可，1..最大值 | `src/firmware/FirmwareDeadline.ts Type：FirmwareDeadline`、`src/firmware/FirmwareFailures.ts 函数：firmwarePhaseInterruption 偏移：+0` |
