# 03 · 最小例子：一次全路径走读

> 用**一条真实成功的分析请求**把 REA 的六层从入口追到 Evidence 输出：`inspect_apk_signature`（CLI 侧 `rea inspect-apk-signature <path>`）。它属于**本进程内**的制品检查路径 —— MCP 适配器、CLI 适配器、composition 装配根、application 工作流、provider 适配、domain 纯函数各一跳，全都能在源码里追到底。
>
> 边界澄清：本篇**只走主成功路径**，不岔枝（分页、view 选择、取消与清理属第三/四层）。**不要**与 [04 主链路拆解](04-主链路拆解-请求到Evidence.md) 混淆：04 讲「任意一次请求怎么穿过校验/handler/session/cleanup」的通用机制，本篇只把 APK 签名这一条链的**每一跳的形状**摊开。

版本基线同 [00 §9](00-docs-style-guide.md)（提交 `1173c0a9d`，`rea-agents` `6.8.0`）。**本克隆没有 `node_modules/` 与 `dist/`**，因此全文没有任何「我跑出来的输出」：命令行形状取自真实生产代码与 `tests/acceptance/` 的字面 argv，返回值示例一律标 `[推导]`。

## 0 速览

1. 这条链**只有 1 个工具、1 个操作、1 个 provider**：契约 `src/contracts/apkSignature/apkSignatureToolContracts.ts Const：INSPECT_APK_SIGNATURE_CONTRACT`（`name: "inspect_apk_signature"`）、`src/contracts/apkSignature/apkSignatureToolContracts.ts Const：APK_SIGNATURE_TOOL_CONTRACTS`（数组长度 1）、provider 身份 `src/apkSignature/ApkSignatureRelease.ts Const：APK_SIGNATURE_PROVIDER_IDENTITY`（`id: "apk-signature"`、`version: null`）。
2. **一次调用只读一次文件，且全程只读**：唯一的 open 点位于 `src/artifacts/readStableArtifact.ts 函数：readStableArtifact 偏移：+22`，flags 是 `constants.O_RDONLY | constants.O_NOFOLLOW | constants.O_NONBLOCK`（`readStableArtifact+24`）。`src/apkSignature/` 与 `src/domain/apkSignature/` 的非测试文件里 `node:fs` 命中 **0**（§5）。
3. **参数与返回的形状都由 zod schema 定义在 domain 层**：入参 `src/domain/apkSignature/apkSignatureQuery.ts Const：inspectApkSignatureInputSchema`（`path` / `detail` / `view` 三键，`detail` 默认 `"summary"`），出参 `src/domain/apkSignature/apkSignatureReport.ts Const：apkSignatureResultSchema`（`artifact` / `schemes` / `source_stamp` / `posture` / `runtime_execution` 五键）。
4. **MCP 与 CLI 共用同一个 `ApkSignatureService.inspect`**，且都从同一个装配描述子拿实例：`src/composition/apkSignature.ts Const：apkSignatureModule` 的 `create()` 同时被 `src/server/registerApkSignatureTools.ts 函数：registerApkSignatureTools 偏移：+8` 与 `src/cli/apkSignatureCommands.ts 函数：registerApkSignatureCommands 偏移：+54` 调用。
5. **service 不信任 provider 的返回**：`src/application/apkSignature/ApkSignatureService.ts 函数：inspect 偏移：+37` 把 provider 结果再 `apkSignatureResultSchema.safeParse` 一次，并在 `inspect+40` 核对 `report.data.artifact.path === input.data.path`；任一条不满足就报 `AnalysisOutputError`（消息原文见该文件），绝不把 provider 的自述当事实。
6. **CLI 恒取完整 Evidence，summary 由 CLI 适配器自己投影**：`src/cli/apkSignatureCommands.ts 函数：registerApkSignatureCommands 偏移：+58` 写死 `detail: "complete"`；而 MCP 侧的 summary 分支在 `src/application/apkSignature/ApkSignatureService.ts 函数：inspect 偏移：+64` 走 `projectRetainedAnalysis`。同一个「summary」语义有两个 owner —— 见 §7 问题清单 P2。

## 1 为什么选这条链

架构图对 `src/apkSignature/` 的定性是 **in-process APK Signing Block + v1 reader, bounded single read, no device or execution**（[02 §2.4](02-模块地图与依赖方向.md) 的入度 2、1,220 行）。落到源码上有三处直接印证：

| 判据 | 锚点 | 字面内容 |
|---|---|---|
| 装配注释 | `src/composition/apkSignature.ts 函数：createApkSignatureService` | `Compose the in-process APK signature reader without acquisition or import-time I/O.` |
| 端口注释 | `src/application/apkSignature/ApkSignaturePort.ts` `Type：ApkSignaturePort` | `Replaceable offline APK signature reader, independent of device/adb and network.` |
| 固定 limitation | `src/domain/apkSignature/apkSignatureReport.ts Const：APK_SIGNATURE_LIMITATIONS` | `Static structural inspection only. No Android code executes, no device or adb is involved…` |

因此这条链**不经过** `src/process/`（无子进程监督）、不经过 session 绑定、不经过 bridge 协议帧 —— 六跳全部是本机函数调用，是「第一条例应该能一口气读完的链」。

另一个反面事实值得先记下来：**`src/artifacts/ZipArtifactReader.ts` 不在这条链上**。grep 它的使用者只有 `artifacts/inventory/reader.ts`、`artifacts/extraction/ArtifactExtraction.ts`、`flutter/FlutterBuildProvider.ts`、`android/JadxConfiguration.ts`、`browser/history/SazCapture.ts`；签名链自带 ZIP 中央目录解析（`src/domain/apkSignature/apkV1Signature.ts 函数：centralDirectoryV1SignatureEntries`），因为它必须按**字节**而非「解压后的条目」来看签名结构。

## 2 两个入口并列

同一次分析在两侧的调用形状。**字段名**来自真实 schema/argv；**值**除标注外为占位。

### 2.1 MCP 侧：`tools/call`

```jsonc
// → MCP 请求参数（字段名来自 src/domain/apkSignature/apkSignatureQuery.ts Const：inspectApkSignatureInputSchema）
{
  "method": "tools/call",
  "params": {
    "name": "inspect_apk_signature",
    "arguments": {
      "path": "/absolute/path/to/app.apk",   // 必填，绝对路径；schema 里 min(1)
      "detail": "complete",                  // "summary" | "complete"，缺省 "summary"
      "view": { "collection": "signers" }     // 可选，且要求 detail="summary"
    }
  }
}
```

真实证据：`tests/acceptance/apkSignatureViewsCliMcp.test.ts` 里对生产 server 的实际调用就是 `call("inspect_apk_signature", { path })` —— 只给 `path`，因此默认走 `detail: "summary"`，返回值再由 `apkSignatureSummaryViewResultSchema` 解析。

注册链：`src/server/createServer.ts 函数：createServer 偏移：+114`（`apkSignatureModule.create(environment, options.apkSignature)`，见索引）→ `src/server/registerApkSignatureTools.ts 函数：registerApkSignatureTools 偏移：+17` 的 `server.registerTool(contract.name, toolRegistrationOptions(contract), handler(contract))`；`src/server/toolRegistrationOptions.ts 函数：toolRegistrationOptions 偏移：+11` 把 Zod 契约原样投射成 SDK 的 `inputSchema`/`outputSchema`，不做二次改写。

返回：`structuredContent` 是 `evidenceResultOf(z.union([apkSignatureResultSchema, apkSignatureSummaryViewResultSchema, apkSignaturePageViewResultSchema]))`（契约 `Const：INSPECT_APK_SIGNATURE_CONTRACT` 的 `outputSchema`），即「一条完整 Evidence 记录 + 被特化的 `normalized_result`」。Evidence 顶层键（`src/domain/evidence.ts Const：evidenceSchema`）包括 `evidence_id`、`subject`、`provider`、`operation`、`parameters`、`raw_result`、`normalized_result`、`confidence`、`limitations`、`locations`。summary 分支下 `normalized_result` 变成 `{ summary: …, parent_evidence_id: … }` 形态 `[推导]`，依据是 `src/contracts/apkSignature/apkSignatureToolContracts.ts` 的 union 与 acceptance 测试里的 `summary.summary.posture` / `summary.parent_evidence_id` 取值路径。

### 2.2 CLI 侧：真实命令行

```
rea inspect-apk-signature /absolute/path/to/app.apk --json
rea inspect-apk-signature <path> [--detail complete|summary] [--evidence_output <bundle.json>] [--view '<JSON>']
```

- 命令名 `inspect-apk-signature` 来自 `src/cliCommandNames.ts Const：CLI_COMMANDS` 里的 `inspectApkSignature` 键（`inspectApkSignature: "inspect-apk-signature"`），由 `src/cli/apkSignatureCommands.ts 函数：registerApkSignatureCommands 偏移：+5` 的 `cli.command(apkSignatureModule.cliCommand, …)` 注册。
- `path` 是**位置参数**（在 `args: z.object({ path: localPathStringSchema… })` 里，不在 `options`）。真实 argv：`tests/acceptance/apkSignatureV1Cli.test.ts` 的 `["inspect-apk-signature", path, "--json"]`。
- `--json` `[推导]` 由 **依赖：incur** 的框架输出层提供：`src/cli.ts` 与 `src/cli/apkSignatureCommands.ts` 里都没有定义 `json` 选项，测试却稳定用 `--json` 拿机器可读结果（`complete.json`）。Incur 侧的实现未读取，不臆测其内部细节。
- `--detail` / `--evidence_output` 由 `src/cli/analysisEvidenceDelivery.ts Const：analysisEvidenceDeliveryOptions` 提供，CLI 侧 `--detail` **默认 `complete`**（与 MCP schema 默认的 `summary` 不同源！）。
- `--view` 的 JSON 先经 `src/cli/apkSignatureCommands.ts 函数：registerApkSignatureCommands 偏移：+23` 的 `safeParseJson`，再进 `inspectApkSignatureInputSchema.safeParse`（`registerApkSignatureCommands+41`）；它的 describe 写明「requires --detail summary and --evidence_output」。
- **未实测**：`rea apk-signature --help` 与 `rea inspect-apk-signature --help` 的真实输出（本克隆无 `node_modules/` 与 `dist/`，分发器 `scripts/rea.mjs` 会直接 `exit 1`），待补。

## 4 数据流：从尾部到报告字段

```
bytes（readStableArtifact 一次读入整份文件，≤ 512 MiB，同时得 sha256）
  │
  ├─▶ parseZipTail ──▶ ZipTail{ eocdOffset, centralDirectoryOffset/Size, totalEntries, classicEntryCount }
  │      ├─ 两个以上 EOCD 各自正好结尾      → malformed-zip（目录有歧义：宁可拒，不猜）
  │      └─ EOCD 声明 0 条目却有 local header → malformed-zip（伪装成「未签名」）
  │
  ├─▶ locateApkSigningBlock（判据：cdOffset-16 处 16 字节 magic "APK Sig Block 42"）
  │      null ──▶ v1-only 或未签名
  │      ┌── APK Signing Block 的字节布局 ─────────────────────────────────────────────┐
  │      │ uint64 size │ pair…: uint64 len │ uint32 id │ value bytes … │ uint64 size │magic│
  │      └────────────────────────────────────────────────────────────────────────────┘
  │        按 Const：APK_BLOCK_ID 分派 pair.id：
  │          0x7109871a v2 ─┐   0xf05368c0 v3 ─┐   0x1b93ad61 v3.1 ─┐   0x2b09189e / 0x6dff800d 戳
  │                         ▼                  ▼                    ▼                        ▼
  │              decodeSigners(value,"v2")  decodeSigners(…v3…)  decodeSigners(…v3.1…)  decodeSourceStampCertificate
  │                         └──────────┬───────┴────────────────────┘                        │
  │                                    ▼                                                     ▼
  │              signers[]: certificate / digests[] / signatures[] / min_sdk / max_sdk   source_stamp
  │              v3 另有 rotation.lineage[]（proof-of-rotation：声明，不验证）
  │
  ├─▶ v1 侧（只看中央目录，不解压内容）
  │      centralDirectoryV1SignatureEntries ──▶ META-INF/*.SF 与 *.RSA|*.DSA|*.EC 配对
  │           │  条目名比较用 canonical bytes（zipEntryName.ts 的 decodeZipName / isCanonicalZipName）
  │           ▼
  │      detectV1Signature ──▶ { present, hasManifest, signatureFiles, blockFiles, signers }
  │           ▼
  │      localEntryData（定位条目原始字节）→ inflateRawSync（≤ 1 MiB）→ decodeV1SignatureBlock
  │
  └─▶ computeApkContentDigest(bytes, {tail, blockStart, algorithm})   ← 需要整份 bytes
         └─ 仅当中央目录紧接 EOCD 才重算；否则 matches_apk = null + LAYOUT_LIMITATION
                                    │
                                    ▼
        deriveApkPosture(v1..v3.1 present / signer 指纹集 / selfConsistency) ──▶ posture.*
                                    │
                                    ▼
   result = { artifact, schemes{v1,v2,v3,"v3.1"}, source_stamp, posture, runtime_execution:"not-performed" }
                                    │  （序列化前后各估一次预算，超限直接拒）
                                    ▼
   ApkSignatureService：apkSignatureResultSchema.safeParse ＋ artifact.path/subject 身份核对
                                    ▼
   createEvidence(subject, provider, { operation, parameters:{path}, result,
                                       confidence:"observed", locations, limitations })
                                    ▼
        MCP: structuredContent(normalized_result)     CLI: --json stdout / --evidence_output bundle
```

图上每个节点名都能在 §3 或文末索引里找到锚点；块的字节布局取自 `src/domain/apkSignature/apkSigningBlock.ts 函数：locateApkSigningBlock 偏移：+7`（`trailingSize = u64(dv, cdOffset - 24)`）与 `locateApkSigningBlock+16`（`blockStart = cdOffset - trailingSize - 8`）。

| **契约自述的副作用面** | `src/contracts/toolEffects.ts Const：TOOL_EFFECTS` 里 `inspect_apk_signature: evidence`，而 `const evidence = effects({ mutatesSession: true })` | 除「往会话里追加 Evidence」外，`writesFilesystem` / `launchesProcess` / `accessesNetwork` / `executesForeignCode` / `mutatesDevice` 全为 `false`，`idempotent: true` |
| **域层的 Node 依赖只有纯计算** | 非测试文件里 `src/domain/apkSignature/` 与 `src/apkSignature/` 只 import `node:crypto`（`createHash`、`X509Certificate`）与 `node:zlib`（`inflateRawSync`，`src/apkSignature/apkV1Signers.ts 函数：decodeV1Signer` 的 inflate 点） | 与 [02 §2.1](02-模块地图与依赖方向.md) 的「域层 0 个 fs/child_process」读数一致 |

注意「没有」并不等于「没有边界」：这条链有两个**进程内**闸门 —— `src/apkSignature/ApkSignatureAdmission.ts` 的 `Type：ApkSignatureAdmission`（全进程同时只跑 1 次扫描，排队上限 8）与 `src/apkSignature/ApkSignatureRelease.ts Const：APK_SIGNATURE_LIMITS`（`inputBytes` 512 MiB、`v1BlockBytes` 1 MiB、`outputBytes` 8 MiB）。后者是 AGENTS.md「limits 必须follow 真实格式/资源约束」的落点。

## 6 边界与失败模式

| 现象 | 触发条件 | 锚点 |
|---|---|---|
| `APK signature reader returned malformed data or changed the selected artifact identity.` | provider 的 `result` 过不了 `apkSignatureResultSchema`，或 `artifact.path` 与入参不等，或 subject 身份不匹配 | `src/application/apkSignature/ApkSignatureService.ts 函数：inspect 偏移：+37`、`inspect+40`（身份核对）与 `函数：apkSignatureMatchesSubject` |
| 「signed APK 被报成未签名」被**主动堵死** | 两个 EOCD 各自正好结尾（一个藏在另一个 comment 里）→ 直接拒；EOCD 声明 0 条目但存在 local header → 直接拒 | `src/domain/apkSignature/apkSigningBlock.ts 函数：parseZipTail 偏移：+12`（注释明说比 apksigner 更严：`a crafted APK that apksigner verifies may be refused here, never misreported`） |
| `matches_apk` 静默变 `null` | 中央目录没有紧接 EOCD（声明尺寸不符或中间插了 Zip64 记录），内容摘要**不重算** | `src/domain/apkSignature/apkContentDigest.ts 函数：computeApkContentDigest 偏移：+11`；文案 `src/apkSignature/ApkSignatureProvider.ts Const：LAYOUT_LIMITATION` |
| 重名条目导致 v1 signer 带 `decode_error` | 中央目录里同一名字出现多次；apksig 只读 classic 16-bit 计数声明的前 N 条 | `src/apkSignature/ApkSignatureProvider.ts 函数：duplicateEntriesLimitation`；`classicEntryCount` 在私有 `readV1`（索引 537）里传给中央目录扫描，来源见 `src/domain/apkSignature/apkSigningBlock.ts 函数：parseZipTail 偏移：+63` |
| 「The process-wide APK inspection queue is full…」 | 已有 1 个扫描在跑且排队数达 `waitingScans: 8` | `src/apkSignature/ApkSignatureAdmission.ts` `acquire` 的容量分支（`AnalysisResourceConstraintError(…, "capacity", …)`） |
| 结果被**拒绝**而不是截断 | 序列化前预估 `projectedOutputBytes` 或序列化后 `Buffer.byteLength` 超 `outputBytes` | 两处闸门在 `ApkSignatureProvider` 的私有 `#analyze` 内（`src/apkSignature/ApkSignatureProvider.ts apkOutputBudgetError`；另一处在其后） |
| 相对路径被拒 | MCP 侧 `isAbsolute` 二次把关（CLI 侧先由 `absoluteCallerPath` 规整） | `src/application/apkSignature/ApkSignatureService.ts 函数：inspect 偏移：+19`，消息 `Expected an absolute filesystem path on this host.` |
| `detail: "complete"` 与 `view` 同时给 | schema 的 `superRefine` 直接报 issue（`view requires summary delivery…`） | `src/domain/apkSignature/apkSignatureQuery.ts Const：inspectApkSignatureInputSchema` |
| cleanup 失败后资源**留在手上** | `close()` 里 `ArtifactReaderFailure.cleanup` 存在时抛 `ProviderCleanupError` 并 `bindArtifactFileCleanup` 保住原因 | `src/apkSignature/ApkSignatureProvider.ts 函数：close 偏移：+9`（owner 是 `#resources: ArtifactResourceScope`，注释 `Owns the selected file's descriptor, retaining it when closing fails.`） |
| 未实测：真实 stdout / 体积 / 退出码 | 本克隆无 `node_modules/` 与 `dist/`，`scripts/rea.mjs` 的产物检查会先 `exit 1` | 待补；跑法见 §8 缺口 |

## 7 问题清单

- **P1｜「ZIP 读取」在这条链上有两套表示。** 签名链自带中央目录解析（`centralDirectoryV1SignatureEntries` + `函数：localEntryData`），而 `src/artifacts/ZipArtifactReader.ts` 服务于清单/抽取/flutter/JADX/SAZ。二者对 Zip64、重名、加密位、条目定位各有独立判定，任何一处漂移都会让「同一个 APK 在两个工具里说法不同」。**但**签名侧读字节而非解压内容其实是**正确性要求**（v1/v2 验的是原始条目字节），所以这不是简单的重复。要不要抽公共层？→ **待拍板**
- **P2｜summary 语义有两个 owner。** CLI 恒取 complete（`src/cli/apkSignatureCommands.ts 函数：registerApkSignatureCommands 偏移：+58`），投影在 `deliverCliAnalysisEvidence`；MCP 在 service 里走 `projectRetainedAnalysis`（`src/application/apkSignature/ApkSignatureService.ts 函数：inspect 偏移：+64`）。同一「summary」两条实现路径，`--detail` 的默认值也不同源（CLI `complete` vs schema `summary`）。哪一侧才是真相源？→ **待拍板**
- **P2｜入参被校验三遍。** `src/cli/apkSignatureCommands.ts 函数：registerApkSignatureCommands 偏移：+41` 用同一个 `inspectApkSignatureInputSchema`，`src/application/apkSignature/ApkSignatureService.ts 函数：inspect 偏移：+12` 再来一遍，`inspect+19` 还补一次 `isAbsolute`；而 `src/domain/localPath.ts Const：absoluteLocalPathStringSchema` 本身已经用正则（非 win32 下 `/^\//u`）保证绝对路径，所以 `isAbsolute` 在字面意义上重复。MCP 侧 SDK 也会按 `inputSchema` 校验。防御纵深还是冗余表示？AGENTS.md 要求「在拥有者边界规整一次」，此处是否符合？→ **待拍板**
- **P3｜`requiresActiveTarget: true` 的实际约束面。** [假设] 它只影响能力宣告（`src/application/CapabilityInventory.ts 函数：targetAvailability`），不拦截真实 `tools/call`；未实测。查证方向：在无 session 的情况下对 MCP 直接 `call("inspect_apk_signature", { path })`，看是被拒还是照常出 Evidence（acceptance 测试 `connectLocalToolsMcp()` 的调用路径需要确认其 session 状态）。
- **P3｜串行 admission 在 MCP 常驻进程里的吞吐代价。** `max_active_scans: 1` + 512 MiB 全量读 + 内容摘要需要整文件，意味着 8 MiB 以下 APK 也要排队；第 9 个并发请求直接被拒。是否有量化基线？未读取 `tests/evaluation/`，不臆测。
- **P3｜`apkV1MetadataName.ts` 与 `zipEntryName.ts` 的分工**（大小写敏感的 JAR 名匹配 vs canonical 字节比较）目前只在注释里说明「Case-sensitive throughout, as apksig matches JAR signature entries」（`函数：detectV1Signature 偏移：+6`）。两处规则若不一致会静默漏配对；缺一条把两者钉在一起的回归。→ 待补

## 8 已知缺口

- **风险**：本篇所有「返回值长什么样」都是 `[推导]`。需要一次真实运行（`npm ci && npm run build:cached` 后跑 `rea inspect-apk-signature <apk> --json`）来固定 stdout 形状、`evidence_id` 前缀与 limitations 全量文案。
- **风险**：未覆盖取消与清理路径。`signal` 在 `src/apkSignature/ApkSignatureProvider.ts 函数：inspect`（provider）里被 `assertArtifactReadActive` 检查两次，但最终一致性由 [13 Process 层](13-Process层-子进程监督与所有权.md) 与 [14](14-Filesystem与Windows边界.md) 讲。
- **设计特性（不是缺口）**：`content-digest equality is not cryptographic signature verification`（契约 description 原文），以及 `posture.*` 大量 `nullable` —— 身份未知时宁可 `null` 加一条 limitation，也不猜。这正是 AGENTS.md「未解决的身份必须保持 unknown」的落地。
- 字节级的 v2/v3 块布局、ASN.1 元素上限 `src/domain/apkSignature/apkV1SignatureBlock.ts Const：MAX_ASN1_ELEMENTS` 属第四层；provider 族的对外能力表属 [20 移动与桌面 App](20-移动与桌面App.md)。
