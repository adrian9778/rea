# 02 · 模块地图与依赖方向

> 本篇回答三件事：`src/` 下 50 个目录**各自负责什么**、**谁依赖谁**（用可复现的实测数字，不是感觉）、以及 AGENTS.md 的分层规则**在真实 import 图里是否成立**。
>
> 边界澄清：本篇是「索引」，不解释机制。想看某个机制怎么运行，顺着表里的「详见」跳到对应篇。

## 0 速览

1. 依赖的**汇聚点是 `src/domain/`**：全仓库有 **1094 个**非测试文件（`src/domain/` 之外）从它 import，是第二名 `src/application/`（293）的近 4 倍。
2. Provider 目录的 fan-in 普遍极低（`captures`/`adb`/`apktool`/`objdump` 各 **1**，`hopper`/`jeb`/`kuna`/`ida`/`apkSignature` 等各 **2**），多数是因为**只有装配根被允许认识它们** —— `src/composition/` 的 fan-in 是 48，正好承接这批集中依赖。例外是会话/调试器族（`gdb` 3、`rizin` 4、`frida` 3），`src/server/` 与 `src/cli/` 也会直接 import，见 [17 篇问题清单](17-Native与调试器Provider族.md)。
3. `src/cli/` 的 fan-in 是 **0**（把 `src/cli/` 与根级 `src/cli*.ts` 视为同一个 CLI 适配器组）：组外没有任何模块 import 它；组内的 `src/cli.ts` 会 import `src/cli/*Commands.ts`。它只被 `dist/cli-runtime/cli.js` 作为入口直接执行（[01 §5](01-系统骨架.md)）。
4. **`src/artifacts/`（231）与 `src/filesystem/`（147）是第三、第六大的被依赖模块**，但 `docs/architecture.mermaid` 里只用一个 `AUX` 节点把它们和别人混着讲 —— 这是既有架构文档的口径缺口，本篇补齐。
5. 架构图的 113 条依赖边里，有 **4 条**是「application 直达具体 provider 目录」（`APP --> FIRMWARE`、`APP --> ANDROID`、`APP -->|EVM interface port| EVM`、`APP --> REFERENCE`），与 AGENTS.md「Keep engine protocols and provider-specific code out of domain/application layers」存在**口径张力**，见 §6 问题清单 P1。

## 1 度量怎么来的

表里的 `入度` 列 = 「`src/<模块>/` 之外，有多少个非测试 `.ts` 文件在路径解析后真正指向该模块」。复现脚本（在仓库根执行）：

```bash
python3 - <<'PY'
import re, pathlib, posixpath
root = pathlib.Path("src")
fans = {}
for f in root.rglob("*.ts"):
    if f.name.endswith(".test.ts"):
        continue
    top = f.relative_to(root).parts[0]
    seen = set()
    for m in re.finditer(r'from\s+"(\.[^"]+)"', f.read_text(errors="replace")):
        p = posixpath.normpath(posixpath.join(str(f.parent), m[1])).split("/")
        if len(p) > 1 and p[0] == "src" and p[1] != top:
            seen.add(p[1])
    for t in seen:
        fans[t] = fans.get(t, 0) + 1
for k, v in sorted(fans.items(), key=lambda kv: -kv[1]):
    print(v, k)
PY
```

三个已知失真，读数时记住：

- **按文件计数，不是按 import 语句计数**：一个文件引用同模块 10 次仍算 1。
- **不统计别名/桶文件**：如果存在 `export * from "../artifacts/x.js"` 型的中转文件，只算直接那一跳。
- **不统计 `dist/` 与测试**：测试文件被排除，因此「测试替身注入」这类依赖不在图里。

方法上有一条必须记住的修正：**不要用「`from "../<模块>/` 前缀 grep」代替路径解析**。同名的子目录会让前缀匹配误报（`src/domain/native/…` 被算成 `src/native/`），根级 `./domain/…` 又会被漏计。本表数字由上面的脚本逐文件 `normpath` 得到；早期用前缀 grep 估出的 `native 40`、`javascript 16` 都偏高，已按实测修正。

行数与文件数口径：`find src -name '*.ts' -not -name '*.test.ts'`，基线提交 `1173c0a9d`。

## 3 依赖方向：图画了什么，没画什么

`docs/architecture.mermaid` 共 214 行、**113 条边**（含 `TESTS -.->` 虚线边）。它自己第一行就声明了口径：

> `Selected layer owners and dependency/wiring paths, not a directory or import inventory.`

也就是说它是**选型图**，不是 import 清单。把两种口径并排看，能立刻看出缺口：

```
架构图的边（113 条，人写的选型）      实测 import 入度（工具算的）
────────────────────────────────┼──────────────────────────────
DOMAIN       ← 14 个节点指向它   │ 1094 个文件指向它
APPLICATION  ← CLI/MAIN/SERVER   │  293
ARTIFACTS    ← 只在 AUX 节点里    │  232   ★ 图里没有独立节点
FILESYSTEM   ← PROCESS/AUX/APP    │  148   ★ 排在 contracts 之后
PROCESS      ← 几乎每个 provider  │  170
CONTRACTS    ← ERRORS/ANDROID…    │  155
COMPOSITION  ← CLI/MAIN/SERVER    │   48
单个 provider │ 各自 1~4          │   多数 1~2，调试器族 3~4
```

★ 标记的两项是本篇相对既有架构文档的主要补全。

## 4 谁认识谁：装配的集中度

一个反直觉但很关键的读数：**provider 目录几乎不被业务代码 import**。

```
              ┌──────────── src/cli.ts ────────────┐
调用方 ──────▶│                                    ├──▶ src/composition/  (入度 48)
              └──────────── src/main.ts ───────────┘            │
                                                                ▼
                        ┌───────┬───────┬───────┬───────┬───────────┐
                        │hopper │ ghidra│  ida  │ kuna  │ adb/apk…  │   入度 1~4
                        └───┬───┴───┬───┴───┬───┴───┬───┴─────┬─────┘
                            │       │       │       │         │
                            ▼       ▼       ▼       ▼         ▼
                       src/process/  src/filesystem/  src/contracts/  src/domain/
                          (170)          (148)           (155)          (1094)
```

含义：换掉/新增一个 provider 的**改动面收敛在装配根**，这是 AGENTS.md「one-shot binding and independent optional loading」在 import 图上的可观测结果。[推导] 入度低（多数 1~2）是「独立可选加载」能成立的前提，因为不存在第二条路径能让别处的代码直接 new 一个 provider。

例外要如实记：`src/artifacts/`（232）和 `src/native/`（25）**不是**只被装配根认识 —— 它们被 application、browser、ghidra 等多处直接使用，因为它们承担的是「共享 reader/清单」职责而非引擎协议。`src/providers/`（19）同理。

## 5 边界与失败模式

| 现象 | 判据 |
|---|---|
| 某目录看起来「没人用」 | 先查入度是否为 0 **且** 是否出现在 `scripts/rea.mjs` 的产物清单或 `package.json#bin` 里（`src/cli/` 就是这种情况：入度 0 但它是入口） |
| 想判断两个目录谁该依赖谁 | 别只看行数；用 §1 的命令实测入度，再对照 `docs/architecture.mermaid` 的边 |
| 把 `docs/architecture.mermaid` 当 import 清单 | 图自己声明了不是；它省略了 `src/artifacts/`、`src/filesystem/` 等节点的独立边 |

## 6 问题清单（含待拍板）

- **P1｜application 直达 provider 的 4 条边**。`APP --> FIRMWARE`、`APP --> ANDROID`、`APP -->|EVM interface port| EVM`、`APP --> REFERENCE`。AGENTS.md 要求「引擎协议与 provider 专有代码不得进 domain/application」。需要区分：这 4 条是**端口注入**（application 定义端口、composition 注入实现，符合规则）还是**直接 import provider 模块**（违反规则）。判据要看 import 语句里出现的是 `../application/x/FooPort.js` 还是 `../firmware/…`；[未知] 目前只有架构图给了方向，未逐条回源码验证。→ 由 [12](12-Application层-共享工作流.md) 与 [21](21-固件抓包与存储格式.md) 各证一部分。
- **P2｜3 个目录没有独立架构节点**：`src/artifacts/`、`src/filesystem/`、`src/providers/` 中后两者已入图，`src/artifacts/` 只出现在 `AUX` 合并节点里。是否补节点由维护者决定；本篇先把实测数字摆出来。
- **P3｜`src/compression/`(23 行) 与 `src/objdump/`(29 行) 值不值得成目录**：都是单文件公共件，引用点极少。是设计特性（把 codec 结果规整独立出来）还是历史遗留 —— 源码未回答。→ 待拍板

## 7 已知缺口

- **入度口径是「文件数」，不是「依赖强度」**：一个文件 import 同模块 10 次仍记 1，所以入度只能回答「有多少外部文件认识它」，不能当耦合度排序。§1 已列三条已知失真。
- **`docs/architecture.mermaid` 是人工选型图，不是 import 图**：它省略了 `src/artifacts/`、`src/filesystem/` 的独立边，也不画 `src/cli/` 的入口关系。本篇实测数字与图不一致时，讨论设计口径以图为准，改代码时以实测 import 为准。
- **行数与入度是快照**：基线提交 `1173c0a9d`；后续增删目录会让表里的数字过期，复现命令在 §1。
- **动态 import 未进表**：§1 的命令只匹配静态 `from "..."`；源码里另有 113 处 `import(` / `await import(` 文本匹配（本会话 grep 计数，未逐条分类），它们若构成运行时依赖不会体现在入度里。
- **类型-only 依赖未剔除**：`import type` 同样匹配统计命令，因此入度是「认识」而不是「运行时加载」。
